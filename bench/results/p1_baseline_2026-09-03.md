# P1 governed-ledger baseline — 2026-09-03

This report records the first reproducible performance baseline for the 0.4.0
vertical governed-act cycle. It is a diagnostic baseline, not a release claim.

## Environment

- Elixir 1.20.2
- Erlang/OTP 29
- x86_64 Linux
- 18 online BEAM schedulers
- local ETS and local filesystem Disk adapters

Each complete cycle submits one materially distinct Candidate, obtains its Act,
consumes its Grant into an Attempt, records trusted executor Evidence, and records
a successful Outcome. Setup and one warm-up sample are excluded from the 1/10
measurements. The 100-proponent diagnostic uses one cold sample because the
current implementation is already beyond its practical saturation point.

## Commands

```sh
mix run bench/p1.exs -- --stores ets --proponents 1,10 --samples 3 --warmup-samples 1 --stream-segments 64
mix run bench/p1.exs -- --stores ets --proponents 100 --samples 1 --warmup-samples 0 --stream-segments 0
mix run bench/p1.exs -- --stores disk --proponents 1,10 --samples 3 --warmup-samples 1 --stream-segments 32
mix run bench/p1.exs -- --stores disk --proponents 100 --samples 1 --warmup-samples 0 --stream-segments 0
```

Group mode uses a maximum Admission batch of 64 Candidate transactions and a
1 ms wait. Individual mode uses a batch of one and no wait.

At 10 proponents, group commit reduces Admission from 10 appends to one append;
the mean Admission batch is 10 Candidate transactions and 40 ledger entries. At
100 proponents, it uses two appends with a mean of 50 Candidate transactions and
200 entries. Attempt, executor Evidence, and Outcome remain one append each per
completed cycle in both modes.

The materially distinct sequential streaming floor was:

- ETS, 64 segments: 2.305 segments/s; Candidate-to-Attempt p50 185.490 ms,
  p95 584.145 ms, p99 1004.138 ms.
- Disk, 32 segments: 4.485 segments/s; Candidate-to-Attempt p50 116.095 ms,
  p95 205.234 ms, p99 224.831 ms.

## Decision

The current implementation is a **no-go for release performance**. Saturation is
already visible at 10 proponents and the 100-proponent point confirms severe
history-dependent growth. Grouping Admission works, but does not improve the
complete-cycle rate once Attempt, executor Evidence, and Outcome serialize behind
the same Domain process and each causes another append and materialization.

The similar ETS and Disk curves indicate that storage durability is not the
dominant cost in this environment. Keep one authoritative ledger per Domain as
the semantic model, but do not freeze the current Sequencer/projection shape as
the 0.4.0 runtime. Profile and remove repeated full-history semantic work from the
hot path, reduce the Sequencer to ordering/evaluation/append/Grant, and rerun this
same matrix before changing batch or backpressure defaults.

The 100-proponent rows contain a single sample and therefore diagnose scale, not
variance. Hardware-specific release thresholds still need a later controlled
benchmark environment.
